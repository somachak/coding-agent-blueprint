Build a Coding Agent From Scratch

A course that ends in a blueprint: a bare-bones, model-agnostic coding agent in plain Python, with a single chat window that shows every step it takes. Every code block on this page is the real file, embedded at build time. Nothing here is a quiz; each idea is explained directly, then shown running.

How to read this

Each chapter adds exactly one mechanism. For each one you get: what it is for, a picture, the code, a command to run it, and a list of what breaks if you take it out. The "what breaks" lists are the troubleshooting course in disguise: when the agent misbehaves later, the symptom will be on one of those lists.

0 · The map: five parts, one loop

A coding agent is not a special kind of model. It is an ordinary model, called over and over, with a list of messages that grows and a handful of Python functions it is allowed to ask for. The whole design fits in one picture.

The loop in the middle knows nothing about HTTP and nothing about files. It knows three things: messages go in, a message comes out; if the message asks for tools, run them and append the results; otherwise stop. That ignorance is deliberate. It is why the same loop can drive a terminal, a web page, or your own application, and why the tools can be swapped for anything.

Setup: three things, then everything runs

  1. Python 3.11 or newer. Nothing to install: the whole blueprint uses only the standard library.
  2. A key. Copy .env.example to .env and paste an OpenRouter key into LLM_API_KEY. Any OpenAI-compatible endpoint works too (OpenAI, Groq, a local Ollama); change LLM_BASE_URL and LLM_MODEL.
  3. A model that supports tools. The default is openai/gpt-5-mini. Cheaper: openai/gpt-5-nano. Free (rate-limited): google/gemma-4-31b-it:free. If a model answers in prose instead of calling tools, that is the model, not your code (chapter 9, case 10).

The workspace

The agent may only touch the workspace/ folder. Put a small project in there to play with, or let the agent create one. Delete its contents whenever you like.

1 · One call to the model

Before there is an agent there is a single HTTP request. Chapter 1 is that request and nothing else. Three things go out: which model, a list of messages, and the key that proves you may ask. One thing comes back: a JSON document with the model's message inside it.

The words to own here: a message is a dictionary with a role and content. JSON is the text form of dictionaries and lists that travels over HTTP; json.dumps makes text from Python, json.loads makes Python from text. The model does not see Python. It sees text.

The code: course/ch01_one_call.py
python3 course/ch01_one_call.py

What breaks if you remove it

  • No Authorization header → HTTP 401. The server does not know who is asking.
  • A wrong model id → HTTP 400 or 404. Read the body; it names the problem.
  • An empty messages list → HTTP 400. There is nothing to answer.

2 · The list that grows (memory is not in the model)

A chat is chapter 1 inside while True, plus one rule: every message, yours and the model's, is appended to the same list, and the whole list is sent every time. The model has no memory. Each call starts from zero. It only appears to remember because you keep handing it the transcript.

0 · system
You are a friendly assistant.
1 · user
My name is Soma.
2 · assistant
Nice to meet you, Soma!
3 · user
What is my name?
4 · assistant
Your name is Soma.

That is the real transcript from running the chapter. On the second question the model was sent all four earlier cards. Delete the line that appends the assistant's reply (marked (A) in the file) and it will still answer, but it will have forgotten what it just said, because you never showed it.

The code: course/ch02_chat_loop.py
python3 course/ch02_chat_loop.py

What breaks if you remove it

  • Stop appending the assistant reply → the model contradicts itself, and later chapters get HTTP 400 because tool results answer requests that are no longer in the list.
  • Stop appending the user message → the model answers the previous question again.

3 · The first tool (this is the chapter where it becomes an agent)

A tool is a normal Python function. The model cannot run it. What the model can do is write a small piece of JSON that says "please call this name with these arguments". You run the function, put the result back into the list as a tool message, and call the model again. That round trip is the entire trick.

4 · The loop


Chapter 3 did one round trip by hand. Real tasks need several, and nobody knows how many in advance. So the round trip goes inside while True with one stopping rule and one brake:


    

  • Stop when the reply has no tool_calls. That reply is the answer.
    • 

  • Brake after MAX_STEPS model calls. A model can get stuck asking for the same thing forever, and every call costs money.
    • 






Notice what the loop does not contain: no knowledge of what a file is, no HTTP details, no special cases per tool. The lookup table FUNCTIONS turns a name into a function; the loop calls whatever it finds. Adding a tool never touches the loop again.



The code: course/ch04_the_loop.py


python3 course/ch04_the_loop.py


What breaks if you remove it


    

  • Remove the break on "no tool calls" → the loop asks the model again with nothing new; it repeats itself until the brake stops it.
    • 

  • Remove MAX_STEPS → a stuck model runs, and bills you, until you kill the process.
    • 

  • Handle only tool_calls[0] → the model often asks for several tools at once (chapter 4's run asked for five reads in one go); the unanswered ones cause HTTP 400 on the next call.
    • 





5 · The registry, and the five tools that make it a coding agent


Chapter 4's lookup table becomes the centre of the design. One table, two halves side by side: on the left, the schema the model reads; on the right, the function we run. If a name is in one half and not the other, the agent breaks in a very specific way (chapter 9, case 1).





Why these five and not more: Pi, one of the strongest minimal agents, ships four (read, write, edit, bash). Thorsten Ball's teaching agent ships three. Everything else (grep, git, tests, installs) is reachable through run_command. Why not fewer: without edit_file the model rewrites whole files and clobbers what it did not mean to touch; without read_file with line numbers it cannot quote exact text to edit.



Three rules the loop depends on


    

  1. Every path is checked. safe_path resolves .. and symlinks with os.path.realpath and refuses anything outside the workspace root. Text checks like "does it start with the folder name" are not enough: a symlink inside the folder can point anywhere.
    2. 

  2. Every tool returns text, even when it fails. An exception would crash the loop. An error message goes back to the model, which reads it and tries something else. Chapter 5's live run shows this: the model ran python countdown.py, got exit code 127: python: command not found, and on the next step ran python3.
    3. 

  3. Big outputs are cut in the middle. The model needs the start (what happened) and the end (where it failed). The middle of a 50,000-character log only wastes the context window.
    4. 




The code: course/ch05_registry_and_coding_tools.py


python3 course/ch05_registry_and_coding_tools.py


What breaks if you remove it


    

  • The try/except in run_tool → one bad argument from the model crashes the whole program.
    • 

  • safe_path → "read ../../.ssh/id_rsa" works.
    • 

  • The uniqueness check in edit_file → the model changes the wrong occurrence, silently.
    • 

  • The timeout in run_command → a command that waits for input (python3 with no file) hangs the agent forever.
    • 

  • truncate_output → one pip install log fills the context window.

6 · Events: the moment the script becomes a reusable blueprint


Chapters 1 to 5 were one growing script with print() inside the loop. That is fine for a terminal and useless for anything else: a web page, a log file, or your own app cannot see print(). So the loop stops printing and starts reporting. Every time something happens it calls a function you handed it, with a small dictionary describing the event.





That one change is what turns the script into the package in agent/. Read the loop below and check it against chapter 4: it is the same loop with on_event(...) where the prints were, wrapped in a class so the message list has somewhere to live between user messages.

7 · The web window


agent/server.py is a small HTTP server from the standard library with four routes. Three of them are one line each. The fourth, POST /chat, is where the events go to the browser: instead of one JSON reply at the end, the server keeps the connection open and writes one line per event as the loop reports it.





The page has two tabs on the right. Loop, step by step draws one card per event: Reason, Act, Observe, Answer. Messages the model sees is the exact list from GET /state, so you can check with your own eyes that every tool message answers a tool call by id. When something goes wrong, that tab is the first place to look.

The Settings button lets you point the page at a different agent server, and paste a key, base URL and model that override .env for this conversation. Those values live in your browser and in the server's memory only; nothing is written to disk.




8 · Context: what the model sees first, and what to do when the list gets long


The system prompt


Message 0 is sent on every call and holds the standing rules: look before you touch, edit precisely, run to check, summarise at the end. If the workspace contains an AGENTS.md file, its text is appended. That is how a project teaches the agent its own conventions without anyone changing Python. See build_system_prompt in agent/__init__.py.



Compaction


The list only grows, and every model has a window. Quality drops well before the hard limit. So before each model call the Agent estimates the size (about four characters per token, which is honest enough to decide when) and, past 80% of the window, shrinks the old part in two increasingly drastic steps.





One rule must never be broken: a tool message stays right after the assistant message that asked for it. So the cut is only ever placed at a user or assistant message, never at a tool message. find_cut_index in agent/context.py is where that rule lives, and it has its own test.



The code: agent/context.py


Watch it happen: course/ch08_context_window.py (offline)


python3 course/ch08_context_window.py


What breaks if you remove it


    

  • No compaction → after enough steps, HTTP 400 "context length exceeded", and quietly worse answers long before that.
    • 

  • Cutting at a tool message → HTTP 400: a tool result without its tool call.
    • 

  • Estimating with the cumulative usage counter → you fire compaction far too early (the course this blueprint is based on shipped that bug and fixed it).
    • 





9 · The troubleshooting lab


This is the chapter for the day the agent inside your own app "does not give answers". Twelve failures, each reproduced with the fake model in course/ch09_troubleshooting_lab.py, so you can see the symptom on a machine that is not on fire. The table is the map; the file is the lab.





#Symptom you seeCauseWhat the blueprint does / what to check


1A tool result says "there is no tool called X"The model asked for a name that is not in the registry (schema and registry drifted, or the model invented one)Registry miss becomes text; the model retries. Check both halves of the table use the same name.


2"arguments were not valid JSON"The reply was cut off (finish_reason == "length") or the model emitted broken JSONText error, model retries. If it repeats, raise max_tokens or shorten what you ask for.


3"wrong arguments for X: unexpected keyword"Schema property names do not match the function's parameter namesMake them identical. The TypeError is caught and reported.


4"is outside the workspace and was refused"The model used .. or a symlinkWorking as designed. If it keeps trying, put the absolute workspace path in the system prompt (it is there by default).


5edit_file: "not found" / "appears N times"The model paraphrased instead of quoting, or the text is not uniqueThe error tells it to re-read and copy exactly. Line numbers in read_file exist for this.


6"Stopped after N steps without a final answer"The model loops on the same toolThe brake. Read the Messages tab: what did it keep asking for? Usually a tool result it could not act on.


7Answers get vague; HTTP 400 context lengthHuge tool outputs or a very long sessiontruncate_output and compaction. Check AGENT_CONTEXT_WINDOW matches the model.


8The agent hangs on a commandThe command waited for inputThe timeout kills it and reports it. Tell the model to pass timeout_seconds or avoid interactive commands.

The five questions to ask, in order, when it "gives no answer"


    

  1. What did the last event say? (error events carry the HTTP hint; answer events carry an empty string if the model chose to say nothing.)
    2. 

  2. Open Messages the model sees. Does every tool message answer a request just above it?
    3. 

  3. What did the last tool result say? The model can only act on what that text told it.
    4. 

  4. Is the model one that supports tools, and is the key allowed to use it?
    5. 

  5. Replay the same steps with the fake model. If it works there, the loop is fine and the model is the variable.
    6. 





10 · Your own tools: the blueprint in someone else's app


Nothing in agent/loop.py knows about files. It knows about a ToolRegistry. To reuse the agent in another application (a formulation assistant, a support bot, a data checker) you write new tools and keep everything else. The recipe is always the same four steps.


    

  1. Write plain functions. Text or JSON-able values in, text out. Return error messages rather than raising, for anything the model could fix by trying again.
    2. 

  2. Describe each one with a Tool(...). A name, a description written for the model (say when to use it), and JSON-schema parameters whose names match the function's parameters exactly.
    3. 

  3. Put them in a ToolRegistry and hand it to Agent(...).
    4. 

  4. Write a system prompt that says what the agent is for and what it must never guess.
    5. 






The code: course/ch10_your_own_tools.py (offline)


python3 course/ch10_your_own_tools.py



Transplant checklist (for your own app)


    

  1. Copy the agent/ folder into your project. Keep loop.py, tools.py, llm.py, config.py, context.py, fake_llm.py, debug.py. Keep workspace.py only if your app needs file tools.
    2. 

  2. Write your tools as in chapter 10. Give each one a test with the fake model: script one call, assert the function ran and the answer came back.
    3. 

  3. Build the agent once per conversation: Agent(llm=..., tools=ToolRegistry([...]), system_prompt=..., max_steps=..., context_window=...). One Agent object is one conversation; keep one per user session.
    4. 

  4. Wire on_event to wherever your app shows progress. The event types are listed at the top of agent/loop.py.
    5. 

  5. Before shipping, run chapter 9's five questions against a real failing conversation. Add check_message_order to your logging on any HTTP 400.
    6.

Two honest limits

The cloud sandbox sleeps after 15 idle minutes and forgets its files and conversation; that is what makes it cheap. And a coding agent runs whatever commands the model chooses, so the hosted page is behind a password. On your own machine the workspace lock is a convenience, not a security boundary: the commands run as you.




Glossary




TermMeaning here


MessageA dictionary with a role (system, user, assistant, tool) and content. The unit the model reads.


Tool callA piece of JSON in an assistant message that asks for a function by name with arguments as a JSON string. It carries an id.


Tool messageThe result of running a tool, sent back with tool_call_id so the model knows which request it answers.


SchemaThe description of a tool the model reads: name, description, parameters (JSON Schema). The model never sees the Python.


RegistryThe dictionary from tool name to Tool. Looking a name up is not running it; run() is.


The loopCall the model; if it asked for tools, run them and append the results; repeat; stop when it answers with text.


StepOne model call inside the loop. max_steps is the brake.


EventA small dictionary the loop hands to on_event whenever something happens. How every interface, terminal or web, watches the loop.


WorkspaceThe only folder the tools may touch. Checked with realpath on every call.


Context windowHow much the model can read at once. Compaction keeps the list under 80% of it.


CompactionShrinking the old part of the list: blank old tool results, then summarise. The recent tail stays verbatim.


System promptMessage 0: standing rules, plus the workspace's AGENTS.md if present.


Fake modelA scripted stand-in for the model, used by tests and the offline chapters.


SSEServer-Sent Events: "data: …" lines written to an open HTTP connection. How the web page gets events as they happen.
